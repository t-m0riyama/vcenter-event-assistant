# 構成変更の検出の仕組み

> 本書は、[構成変更を目立たせる（タイムライン）](../plans/2026-11-24-config-changes.md)の計画に基づき、検出の仕組みを説明するものです。実装は同計画の PR B（API）と PR C（画面）で行います。実装の完了までは、本書の内容は予定であり、細部は実装に合わせて改めます。

タイムラインは、表示期間の中で行われた構成変更を、イベントのスコアに関係なく検出します。検出した変更は、ハイライトの「構成変更」のカードにまとめて表示します。時系列の一覧では、該当する行に「構成変更」の印を付けます。障害の調査で最初に確認したい「直前に何を変えたか」に、すぐ答えられるようにすることが目的です。

## 1. 検出が必要な理由

構成変更を示すイベントとタスクは、すでに vCenter から収集しています。しかし、そのほとんどはスコアが 0 点のため、タイムラインに表示されていませんでした。

- イベントのスコアのうち、重大度による加点は、重大度を持つ EventEx にしか付きません。VM の再構成やメンテナンスモードのような通常のイベントは、多くが 0 点です。
- タスクの成功（`task.success.<操作>`）も 0 点です。
- タイムラインは、既定ではスコアが 1 以上のイベントだけを表示します。

このため、構成変更は最小スコアとは別の基準で検出します。

## 2. 検出の対象は組み込みの一覧で決めます

検出の対象は、本体に組み込んだ固定の一覧で決めます。一覧は、変更の種類ごとに、表示名、イベントの種別、タスクの操作を持ちます。設定の画面からの編集はできません。

| 種類 | 主に含まれる変更 |
|---|---|
| VM の構成変更 | VM の再構成のイベントとタスク |
| メンテナンスモードに入った | ホストとデータストアのメンテナンスモードの開始 |
| メンテナンスモードを出た | ホストとデータストアのメンテナンスモードの終了 |
| クラスタの設定の変更 | クラスタの再構成、DRS と HA の有効化・無効化、アドミッションコントロールの有効化・無効化 |
| ネットワークの設定の変更 | 分散スイッチとポートグループの再構成・作成・削除、標準スイッチの設定 |
| ストレージの設定の変更 | ストレージ I/O コントロール、マルチパスのポリシー、VMFS のマウント |
| リソースの割り当ての変更 | リソースプールと vApp の設定 |
| ホストの設定の変更 | ホストプロファイルの適用、詳細設定、時刻と SNMP の設定、サービスの起動・停止と起動ポリシー |
| ホストのアクセスの設定の変更 | SSH・シェル・DCUI・ロックダウンモード・ファイアウォールの設定 |
| 権限とロールの変更 | 権限の追加・変更・削除、ロールの追加・変更・削除 |
| インベントリの変更 | ホストの追加・削除・移動、名前の変更 |
| アップグレード | VM のハードウェアと VMware Tools、分散スイッチ、Update Manager によるホストのアップグレード |

一覧に含まれるのは、イベント 55 種別とタスクの操作 69 種類です。個々の種別と操作は、計画書の 2 章に記載しています。

次のものは、件数が多いか、構成の変更にあたらないため、対象に含めていません。

- ホストごとに大量に出る HA のイベントとタスクと、vCenter のアップグレード後に全ホストで出る、vCenter のエージェントのアップグレードのイベント
- vMotion と Storage vMotion（既知の障害パターンの検知で扱います）
- スナップショットの作成と復元
- アラームとスケジュールタスクの再構成
- VM の作成・削除・登録

## 3. 判定は種別の完全一致で行います

イベントは、種別（`event_type`）が一覧と完全に一致するときに、構成変更と判定します。タスクは、成功したものだけを対象とし、`task.success.<操作>` の形の種別で照合します。失敗したタスクは、構成変更としては扱わず、通常のスコアに従って一覧に表示されます。

タスクの操作の名前は、vCenter のタスクの説明の一覧（`TaskManager.description.methodInfo`）の形を前提にしています。同じ操作でも、呼び出した対象の型ごとに名前が異なります。たとえば、クラスタの再構成には `ClusterComputeResource.reconfigureEx` と `ComputeResource.reconfigureEx` があります。一覧には、このような型ごとの名前をすべて載せています。

## 4. 検出する期間

構成変更を検出する期間は、表示期間の始まりから、表示期間の終わりと起点のうち早いほうまでです。起点を設定している場合は、起点より後の変更をカードに含めません。起点ちょうどの変更は含めます。

画面から指定する起点はミリ秒単位のため、起点と同じミリ秒内の変更を含めます。表示期間の終わりと同時刻の変更は範囲外です。起点が表示期間の始まりより前にある場合、検出の対象は 0 件です。

vCenter、対象の名前、対象の moid による絞り込みは、ほかのイベントと同じように適用します。表示する種別にイベントが含まれていない場合は、構成変更を検出しません。

## 5. 時系列の一覧での表示

最小スコア以上で表示されていた行のうち、構成変更にあたるものには「構成変更」の印を付けます。この印は、表示期間全体の行に付きます。

表示期間の始まりから起点（または期間の終わり）までの最小スコアに満たない構成変更は、別に読み込んで一覧に加えます。加えた行は、これまでの行とは別に扱い、次の点でこれまでの表示を変えません。

- これまでの行は、従来どおりにまとめ、件数の上限（`item_limit`）で絞り込みます。加えた行は、この処理に含めません。
- 加えた行は、加えた行どうしでだけまとめ、起点または期間の終わりに近いものから一覧に加えます。加える件数は、50 件と件数の上限の少ないほうまでです。この枠は、件数の上限とは別に設けています。
- 一覧の総件数と「打ち切り」の表示は、これまでの行だけで決めます。加えた行を枠で打ち切った場合は、そのことを別の注記で表示します。
- 「最初の兆候」「影響の大きい対象」「新しい種別」の集計では、イベントは最小スコア以上の行を使います。俯瞰グラフのイベント総数には、最小スコア未満のイベントも従来どおり含まれます。

このため、一覧の件数は最大で、件数の上限に、50 件と件数の上限の少ないほうを足した数になります。なお、「起点に最も近い」の印は一覧のすべての行から選ぶため、構成変更の行に付くことがあります。

## 6. ハイライトのカードでのまとめ方

カードには、起点までの構成変更を、関連する行ごとにまとめて表示します。まとめる対象は、最小スコア以上の行と、加えた行の両方です。行を時刻の順に見て、次の順序で既存のまとまりに入れます。どれにも当てはまらない行は、新しいまとまりにします。

1. **同じ一連の処理の行をまとめます。** 本体のコレクタが収集した行で、種類、vCenter、`chain_id` が同じものです。種類が異なる行は、同じ一連の処理でも別のまとまりにします。タスクと、そのタスクの実行に伴って記録されたイベントは同じ `chain_id` を持つため、対象が異なっていても 1 件にまとまります。プラグインが収集した行は、`chain_id` の番号の付け方が本体と同じとは限らないため、この方法ではまとめません。
2. **同じ対象への同じ種類の変更をまとめます。** 種類、vCenter、対象が同じで、まとまりの最後の行から 5 分以内のものです。まとまりの対象には、まとまりに含まれるいずれかの行の対象を使います。両方に moid がある場合は moid で、いずれかに moid がない場合は名前で比較します。ホストが出すイベントと vCenter が出すイベントのように、`chain_id` で結び付かない行をまとめるための規則です。
3. **対象を持たない変更は、利用者でまとめます。** 種類、vCenter、利用者が同じで、まとまりの最後の行から 5 分以内のものです。ロールの変更のように、対象を持たないことがある変更のための規則です。利用者が記録されていない行は、この規則ではまとめません。

間隔は、同じまとまりの行どうしで判定します。間に別の対象の行があっても、まとまりは分かれません。対象の候補が複数ある場合は moid の一致を優先します。名前または利用者が一致する候補が複数ある場合は、最後の行が最も新しいまとまりに入れます。

カードの各項目には、種類の表示名、対象、vCenter、変更した利用者（最大 3 人）、時刻、まとめた行の数を表示します。項目は新しい順に並べ、最大 20 件を表示します。種類ごとの件数もあわせて表示するため、上限を超えた場合でも、ほかの種類の変更があることを確認できます。

この機能より前に保存したスナップショットの結果では、構成変更を判定していません。その場合、カードには「判定していません」と表示します。判定して 0 件だった場合の表示とは区別します。

## 7. 読み込む件数には上限を設けています

最小スコアに満たない構成変更は、新しい順に最大 2,000 行まで読み込みます。上限を超えた場合は、新しい 2,000 行を使ってタイムラインの集計を続け、古い変更を省いたことをカードに表示します。この場合、カードの集計は、追加した行のうち最も古い時刻以降にそろえます。最小スコア以上の構成変更にも同じ期間を適用します。

## 8. 利用者名が表示・保存される場所

カードに表示する利用者名は、個人に関する情報です。表示する場所は次のとおりです。

- **画面:** タイムラインのカードに表示します。イベントの一覧と同じく、閲覧の権限（viewer）を持つ利用者も見られます。
- **調査資料の出力:** Markdown の報告書と、ZIP に含まれる結果の JSON に含まれます。資料を外部に渡す前に、利用者名が含まれていることを確認してください。
- **保存したスナップショット:** 手動で保存したスナップショットの結果にも含まれます。閲覧の権限を持つ利用者も読め、イベントの保持期間を過ぎても、スナップショットの結果の保持期間（既定で 90 日）のあいだは残ります。
- **チャット（LLM）:** 渡しません。

## 9. 制約と注意事項

- **実機のタスク履歴で、操作名の形式を確認しました。** 確認した 10 件のタスクには構成変更がありませんでした。履歴に現れた 4 種類の `descriptionId` は、すべて vCenter のタスクの説明の一覧と一致しました。開発環境のデータベースにあった VM 再構成イベント 3 件には、同じ `chain_id` を持ち、`VirtualMachine.reconfigure` の表示名を含むタスク開始イベントがありました。個々の構成変更の操作名を完了タスクと直接照合できるか、同期的に実行される操作がタスク履歴に残るかは、引き続き確認が必要です。タスク履歴に記録されない操作でも、対象となるイベントが記録されれば検出できます。
- **ホストのアップグレードは、Update Manager によるものだけを検出します。** イメージで管理する vSphere Lifecycle Manager のクラスタで同じイベントが出るかは、確認していません。
- **ホストの起動時に出るイベントがあります。** SSH・シェル・DCUI の有効化のイベントは、設定によってはホストの起動時にも出ます。障害でホストが再起動した後に、構成変更として表示されることがあります。
- **別の変更が 1 件にまとまることがあります。** 同じ対象への同じ種類の変更が 5 分以内に続くと、別の利用者による別の変更でも 1 件にまとまります。利用者名とまとめた行の数を表示するため、まとまったことは確認できます。
- **設定の値の差分は扱いません。** 本機能が示すのは、変更があったことと、その種類・対象・利用者です。何から何に変更したかは、構成の差分を記録する後続の機能（障害調査の 10 案の「案 2b」）で扱います。
