## Context

障害の後に報告書を書いたり、担当を引き継いだりするとき、タイムラインで見た内容を資料として渡したい。今は、イベントやメトリクスを CSV や SVG で個別に出せるだけで、タイムラインの結果をまとめて出す手段が無い。タイムラインの結果とは、出来事の時系列、ハイライト、検知した障害パターン、条件、メモである。

イベント・メトリクス・ログは 7 日で消えるので、7 日を過ぎた障害は再集計できない。手動で保存したスナップショットは、結果ごと残る（既定で 90 日。管理者は結果だけを早く消せる。`INCIDENT_TIMELINE_SNAPSHOT_RESULT_RETENTION_DAYS`）。保存した結果を資料として出せれば、生データが消えた後でも報告に使える。

決めたこと（利用者の決定）:
- **形式:** 障害報告に貼れる Markdown の報告書と、報告書・出来事の CSV・結果の JSON をまとめた ZIP の 2 つ。サーバで作る。
- **範囲:** 手動で保存したスナップショットの結果と、今タイムラインに出している結果の両方を出せる。
- **影響範囲（案 1）:** 含めない（後続）。関係の履歴は 7 日で消え、保存した結果にも入っていないため。

10 案の計画書の注意を引き継ぐ。出力は上限付きの要約であり、障害報告や引き継ぎに添える資料にとどまる。ベンダーのサポートが求めるサポートバンドルの代わりや、SIEM の代わり、唯一の証跡にはしない。

## 1. 前提（コードで確かめたこと）

- **スナップショット:** 表 `incident_timeline_manual_snapshots`（`db/models.py:550`、モデル `IncidentTimelineManualSnapshot`）。
  - 手動（`snapshot_kind="manual"`）で保存すると、サーバが集計し直した結果を `result_payload`（`IncidentTimelineViewResponse` の JSON）に、条件を `view_request_payload` に残す（`api/routes/incident_timeline.py:168-`）。
  - 結果は 8 MiB まで（`MAX_SNAPSHOT_RESULT_BYTES`、同 49 行）。保存のときに、項目の詳細を 2,000 文字に切り詰める（`_truncate_details_for_storage`、`SNAPSHOT_DETAIL_MAX_CHARS`、同 46・52 行）。
  - 自動のスナップショット（`snapshot_kind="auto"`、`services/incident_timeline_snapshot.py:95`）は、条件とアラートの根拠（`trigger_evidence`）だけを持ち、結果を持たない。
  - 保存した結果は `_result_for_response`（同 127 行）で読む。今のスキーマで読めなければ None になる。一覧の `has_result` は `result_payload IS NOT NULL` だけで決まるので、「結果あり」でも読めないことがある。
- **タイムラインの結果**（`api/schemas/incident_timeline_view.py`）: `IncidentTimelineViewResponse` は次のものを持つ。
  - 期間、起点、俯瞰の区切り（`overview`）
  - 出来事（`items`。上限は `item_limit` で最大 1,000 件）、打ち切りの有無と総数（`truncated`・`total_items`）
  - ハイライト（最初の兆候、影響の大きい対象、初めて出た種別、検知した障害パターン（最大 20 件）と総数、判定を省いたパターン）
  - 省いた種別（`omitted_sources`）
  - ログの詳細は、集計の時点で 1,000 文字に切られている（`_LOG_DETAIL_MAX_CHARS`、`services/incident_timeline_view.py:136`）。イベントの内容（`message`）には上限が無い。
- **再集計:** `build_incident_timeline_view`（`services/incident_timeline_view.py`）。期間の検査で 400（760 行付近）、同時実行の上限で 503、行数の上限で 422（784〜792 行）を返す。
- **レート制限:** viewer でも呼べる重い集計は、`main.py:88` の `_RATE_LIMITED_POST_PATHS` で枠（`incident_timeline_view`）に入れている（Issue #301）。パスの一部が変わるものは `_RATE_LIMITED_PATTERNS`（同 106 行。`*` を使える）で数える。
- **409 の前例:** 409 は `auth_deps.refuse_if_principal_switched`（別のタブで利用者が替わった）も返す。理由を見分けるため、`api/routes/alerts.py:161` は `X-VEA-Error-Code` を付けている。
- **サーバでの出力の前例:** ログの CSV（`api/routes/logs.py:88`、`services/log_export.py`）。
  - `time_zone`（IANA 名、既定は UTC）を受け、不正なら 400 にする。
  - `Content-Disposition: attachment` を付ける。`Cache-Control: no-store` は `NoStoreApiCacheMiddleware` が `/api` のすべてに付けている。
  - CSV は UTF-8 の BOM を付け、文字列の列に `neutralize_csv_formula`（同 55 行）を当てる。時刻は `YYYY/MM/DD HH:MM:SS` で、`time_zone` 列と `utc_offset` 列を持つ。
  - 監査のログは書いていない。
- **画面:**
  - 既存の `apiGet`・`apiPost`（`api.ts`）は JSON を返し、Blob は受けられない。
  - 共通の `errorMessageFromResponse` は、500 以上・429・400 を汎用の文言にする。
  - タイムラインの表示の要求は、503 のときに `Retry-After` を見て 1 回だけ再試行する（`api/incidentTimelineView.ts`）。
  - 表示に使った本文は `useTimelineViewController` の `loadedRequest` にある。
  - スナップショットの欄（`TimelineSnapshotSection.tsx`）は既定で閉じていて、保存の部分は operator 以上にだけ出る。
- **権限:** タイムラインの表示と、スナップショットの一覧と詳細は viewer 以上。手動のスナップショットの保存は operator 以上。
- **CSRF:** CSRF のミドルウェアは、認証が有効なときだけ入る（`main.py:291`）。

## 2. 出力の中身

### 中身の原則

- 資料の中身は、viewer が既存の API（タイムラインの表示、スナップショットの詳細）で見られる範囲を超えない。
- 出力した人のユーザー名、表示名、LDAP の DN などは入れない。
- 出力したファイルは、アプリの保持期間の外で残り続ける。この点は文書に書く。

### Markdown の報告書（`report.md`）

見出しの順:

1. **表題と出典**
   - 表題: 「インシデントタイムライン 調査資料」と期間
   - 出力した時刻
   - 出典: 「保存した結果」ならスナップショットの ID と保存の時刻（`created_at`。無ければ `timestamp_utc`）。「今の表示」なら集計した時刻と、「表示の後に集計し直したので、画面と件数が違うことがある」という注記。
   - 注記: 上限付きの要約であり、サポートバンドルの代わりにならない。
2. **条件**
   - 期間、起点
   - vCenter。名前は `items` → `highlights.top_entities` → `highlights.detected_patterns` の `vcenter_name` の順に探し、今の表示に限り DB の今の名前も候補にする。どれにも無ければ ID を書く。`vcenter_id` が無いときは「すべて」と書く。
   - 保存した条件（`view_request_payload`）を読めないときは、期間を結果の `from_utc`・`to_utc` から書き、ほかの条件は「保存した条件を読めません」と書く。`conditions.json` も同じにする。
   - 対象の絞り込みの文字列（`entity`。部分一致）と moid（`entity_moid`）
   - 種別（sources）、`min_score`
   - メトリクスのしきい値（CPU とメモリ。今の集計で使うものだけ）
3. **メモ**（保存した結果のときだけ）
   - スナップショットのメモ（`operator_note`、最大 10,000 文字、複数行）。改行を残すため、フェンスのコードブロックに入れる（無害化の「メモ」を参照）。今の表示では、この節を省く。
4. **概要**
   - 出来事の件数と総数、打ち切りの有無
   - 省いた種別とその理由
   - 種類（イベント・アラート・メトリクス・ログ）ごとの件数。`items` から数え、打ち切ったときは「表示した範囲の件数」と注記する。
5. **ハイライト**
   - 最初の兆候
   - 影響の大きい対象（上位）
   - 初めて出た種別
   - 検知した障害パターン（パターン名、対象、最初と最後の時刻、件数）。総数が 20 件を超えるときは総数を書く。判定を省いたパターン（`omitted_patterns`）も書く。
   - 障害パターンの判定より前（PR #361 より前）に保存した結果は、パターンの欄が空になる。「判定の無い結果」と「0 件」を見分けられないので、その旨を注記する。
6. **注目すべき出来事**
   - 表の列: 時刻、種類、レベル、vCenter、対象、表題（`title`）、詳細（`detail`）、件数、スコア
   - 報告書には最大 100 件を載せる。選び方は、既存の `select_within_limit`（`services/incident_timeline_view.py:528`）の、起点が無いときの優先順位に揃える。
     - 優先の順: レベルの重い順 → 種類の順（アラート → イベント → メトリクス → ログ）→ スコア（None は -1）→ 新しい順 → 入力の順
     - ログの上限は既存と同じく `100 - min(ほかの種類の候補の件数, 25)` にする（ほかの種類が少なければ、空いた枠をログで埋める）。選び方の本体は `select_within_limit` と共有する。
     - まず warning 以上から選び、選べた件数が 100 件に満たないときだけ、残りの枠を info で同じ規則のまま埋める。
     - 起点は使わない（資料は期間全体の要約なので）。
     - 選んだ後は、`items` の順（時刻、種類、元の ID）に並べる。
   - 表の前に書く文言は、打ち切りの有無で分ける。
     - 打ち切っていないとき: 「全 N 件のうち M 件。全件は ZIP の items.csv にある」
     - 打ち切ったとき: 「総数 T 件のうち、表示した N 件を ZIP の items.csv に入れた。報告書の表はそのうち M 件」
     - Markdown だけを出力したときは、「items.csv にある」の代わりに「ZIP の出力にある」と書く。

### 時刻

- 時刻は、要求の `time_zone`（IANA 名、既定は UTC）で、`YYYY/MM/DD HH:MM:SS +09:00` のように、時刻ごとに UTC からのずれを付けて書く。夏時間のあるタイムゾーンでも、切り替わりをまたぐ時刻が曖昧にならないようにするためである。
- `time_zone` が不正なら 422 にする（ログの CSV は 400 だが、画面が理由を出せるよう、本文に理由を持つ 422 にする）。検査は、集計の前に行う（無駄に集計の枠を使わないため）。

### 外から来た文字列の無害化

**対象:** アプリが組み立てる列挙値（種類、レベルなど）と数値以外の文字列は、すべて外から来たものとして扱う。たとえば次のもの。
- イベントの内容、種別（`event_type`）、表題（`title`）
- ログの本文
- 対象の名前と種別、vCenter の名前
- アラートのルール名
- 障害パターンの表題と説明
- メモ
- 条件の `entity`。URL のハッシュから入るので、細工したリンクを共有されると、相手が出力した資料に任意の文字列が入る。

**対象とする表示系:** GitHub と GitLab（GFM）と、CommonMark。Jira（ウィキ記法）や Redmine の Textile は対象外にする。そこへ貼るときは、コードブロックに入れるか、ファイルを添付するよう文書に書く。

**手順:** どの文字列も、次の順に処理する。
1. **1 行に正規化する。**
   - 改行（`\n`・`\r`・U+2028・U+2029）とタブは、空白にする。
   - 制御文字（Unicode の一般カテゴリ Cc。C0、DEL、C1）は、取り除く。
   - 書式の文字（Unicode の一般カテゴリ Cf）も、取り除く。双方向の制御文字（U+200E・U+200F・U+061C、U+202A〜U+202E、U+2066〜U+2069。表示の順を偽装できる）、ゼロ幅の文字（U+200B〜U+200D、U+FEFF）、U+2060、タグ文字（U+E0001 など）を含む（これらはすべて Cf である）。
2. **切り詰める。** 下の表の文字数を超える分は、末尾に「…」を付けて切る。
3. **コードスパンに入れる。**
   - 内容の中で最も長い `` ` `` の並びより 1 つ長い `` ` `` で囲み、両端に空白を入れる。
   - 表のセルでは、`|` を全角の `｜`（U+FF5C）に置き換える。`\|` にする方式は、内容に `\|` があると `\\|` になり、GFM の表がそこでセルを切ってしまう（コードスパンの外に出た残りが Markdown として解釈され、外部の画像やリンクを出せる）ので採らない。見え方は元の文字列と変わるが、元の文字列は `items.csv` に残る。
   - 正規化した結果が空、または空白だけのときは、コードスパンにせず `-` と書く。
   - コードスパンの中では、リンク、画像、HTML、強調、メンション（`@user`）、Issue の参照（`#123`）、自動リンク（素の URL や `www.`）が解釈されない見込みである。
   - 切り詰めをコードスパンに入れた後に行うと、閉じの記号を壊すので、必ずこの順にする。

**メモ:** メモは複数行なので、1 行に正規化せず、フェンスのコードブロックに入れる。改行（`\r\n`・`\r` は `\n` にそろえる）は残し、制御文字（改行とタブを除く）、双方向の制御文字、ゼロ幅の文字は取り除く。フェンスは、内容の中で最も長い `` ` `` の並びより長く、3 個以上にする。

**文字数の上限:**

| 文字列 | 上限 |
|---|---|
| 表のセル（表題、詳細、対象、vCenter の名前など。すべてのセル） | 200 文字 |
| ハイライトの各項目（パターンの表題と説明、対象の名前など） | 300 文字 |
| 条件の `entity` | 300 文字 |
| メモ | 10,000 文字（保存の上限と同じ。切らない） |

**確かめ方:** この方式で十分かは、PR B の初めに、悪意のある文字列の一覧を GitHub の Markdown の表示（`gh api markdown`）で描画して確かめる。一覧に入れるのは、次のようなものである。
- リンク、画像、HTML
- メンション、Issue の参照、自動リンク
- 行頭の `#`・`>`・`-`
- `|`、`\|`、`\\|`、`\\\|`、末尾の `\`、`` ` `` の並び（先頭と末尾も）
- 空の文字列、空白だけ
- 双方向の制御文字

結果は本書に書き足す。足りなければ、方式を直してから実装する。

**確かめた結果（2026-11-24、GitHub の `gh api markdown`、mode=gfm）:** 上の手順で作った表（28 行）と、メモのコードブロックを描画した。

- 表は、すべての行が 3 つのセルのまま描画された（列のずれなし）。`\|`・`\\|`・`\\\|` と、2 回目のレビューで見つかった注入の文字列（`x\|![p](…) @octocat [l](…)`）でも割れなかった。
- 外から来た文字列のセル（26 個。空と空白だけの 2 個は `-`）は、すべて `<code>` の中に収まった。次のものは、1 つも出なかった。
  - 画像（`<img>`）、リンク（`<a>`）
  - メンション（`user-mention`）、Issue の参照（`issue-link`）
  - HTML、見出し、引用、箇条書き、強調、取り消し線、数式、絵文字
  - 素の URL と `www.` の自動リンク
- メモのコードブロックの中に、コードブロックを閉じる試み、画像、メンション、HTML を入れたが、すべて `<pre>` の中にとどまった。後ろの見出しも崩れなかった。

### ZIP（`timeline-<時刻>.zip`）

| ファイル | 中身 |
|---|---|
| `report.md` | 上の報告書（BOM なし） |
| `items.csv` | 表示した出来事（`items`）のすべて |
| `overview.csv` | 俯瞰の区切りごとの件数（`overview`） |
| `result.json` | タイムラインの結果（`IncidentTimelineViewResponse` を `mode="json"` で出したもの） |
| `conditions.json` | 条件（`view_request`）と出典（スナップショットの ID、メモ） |

- **`items.csv` の列:** 報告書の表の列に、ID、種類のキー、moid、終了の時刻、参照（イベントの ID など）を足したもの。
- **CSV の書式:** ログの CSV に揃える。
  - UTF-8 の BOM を付ける。
  - 時刻は `YYYY/MM/DD HH:MM:SS` とし、`time_zone` 列を持つ。時刻の列（開始、終了、ピーク）が複数あるので、ずれは 1 列にまとめず、時刻の列ごとに `<列名>_utc_offset` の列を持つ。
  - `neutralize_csv_formula` は、外から来る列だけに当てる（ログの CSV の `_TEXT_COLUMNS` と同じ考え方）。列は `title`、`detail`、`entity_name`、`entity_type`、`vcenter_name`、`event_type`、`alert_rule_name`、`alert_rule_type`、`alert_state`、`metric_key`、`entity_moid`。数値の列と、ずれの列（`-04:00` など）には当てない（`-` で始まる値を変えるので、壊れる）。
  - ヘッダは英語のキーにする（ログの CSV と同じ）。
  - `overview.csv` も同じ書式にする。
- **ZIP の作り方:**
  - Python の標準の `zipfile`（ZIP_DEFLATED）で作り、依存は増やさない。
  - ZIP の中のファイル名は固定にする（利用者の入力を使わない）。
  - 各ファイルの時刻は、`time_zone` での出力の時刻にそろえる（ZIP の時刻はタイムゾーンを持たないため）。
- **CSV と JSON に入る長さ:** 報告書より長い内容が入る。ただし、ログは 1,000 文字、保存した結果は 2,000 文字で、すでに切られている。

### ファイル名

ASCII だけにする。
- 今の表示: `timeline-<YYYYmmdd-HHMMSS>.md` と `.zip`
- 保存した結果: `timeline-<YYYYmmdd-HHMMSS>-<スナップショットの ID の先頭 8 文字>.md` と `.zip`

時刻は、`time_zone` での出力の時刻にする。

## 3. API（PR B）

| メソッドとパス | 権限 | 内容 |
|---|---|---|
| `GET /api/incident-timeline/snapshots/manual/{id}/export?format=md\|zip&time_zone=…` | viewer | 保存した結果を出力する |
| `POST /api/incident-timeline/export?format=md\|zip&time_zone=…`（本文はタイムラインの表示の要求と同じ） | viewer | 同じ条件で集計し直して出力する |

- **`format`:** `md` と `zip` だけを受ける（それ以外は 422）。
- **Content-Type:** `text/markdown; charset=utf-8` と `application/zip`。
- **応答のヘッダ:** `Content-Disposition: attachment; filename="…"` を付ける。`Cache-Control: no-store` は、ミドルウェアが付けるものに加えて、念のため明示する。
- **保存した結果:**
  - スナップショットが無いときは 404。
  - 結果を持たないときは 409 にし、`X-VEA-Error-Code: snapshot_result_missing` を付ける。結果を持たないのは、自動のスナップショット、古い形式、今のスキーマで読めない結果の場合である。
  - 409 の文言は「結果が保存されていません。開いて再集計してから、今の表示を出力してください。元データの保持期間（既定 7 日）を過ぎていると、再集計の結果は空か一部になります」とする。
- **今の表示:**
  - `build_incident_timeline_view` で集計し直す。400・422・503 はそのまま返す。
  - 集計した結果にも、詳細の切り詰め（2,000 文字）と 8 MiB の上限（超えたら 413）を当てる。保存した結果と同じ大きさに抑えるためである。切り詰めの印と 413 の文言は、出力用のもの（「出力時に切り詰めました」「出力する結果が大きすぎます。期間を狭めるか、種別を減らしてください」）にする。既存の保存用の文言（「保存時に…」）は使わない。
  - Markdown だけの出力は、表が 100 件に抑えられるので、413 を当てない。
- **生成:**
  - 報告書、CSV、ZIP は、メモリの上で `asyncio.to_thread` の中で作る。大きさの検査（切り詰めと JSON の大きさ）と、保存した結果の読み込み（`model_validate`）も、スレッドの中で行う。イベントループを止めないためである。
  - 大きさの山は、結果（最大 8 MiB）のおよそ数倍で見込む。
  - 生成の同時実行は、集計と同じ `aggregation_slot(owner_key)` で抑える。空きが無ければ 503 と `Retry-After` を返す（画面は 1 回だけ再試行する）。レート制限（IP ごと）だけでは、大きな結果を同時に何本も作らせて、メモリを使い切らせることができるためである。
- **レート制限**（Issue #301 の穴を開けないため）:
  - `POST /api/incident-timeline/export` を `_RATE_LIMITED_POST_PATHS` の `incident_timeline_view` の枠に入れる。
  - `GET /api/incident-timeline/snapshots/manual/*/export` を `_RATE_LIMITED_PATTERNS` で同じ枠に入れる（8 MiB の結果の読み込みと ZIP の生成を連打させないため）。`_RATE_LIMITED_PATTERNS` の上の注記（外へ接続して確かめる API の枠）は、重い出力も入ることに合わせて書き直す。
  - テストは、既存と同じく `_rate_limit_spec` を直接呼ぶ形にする（`VEA_PYTEST=1` のときは、ミドルウェアが働かない）。
- **LLM と匿名化:** 出力は LLM を通さない。名前や moid を伏せる処理もしない（利用者自身のデータの出力であるため）。資料を外部に渡すときの注意を、文書に書く。
- **監査:** 監査のログは入れない（ログの CSV と同じ）。アプリのログに、出典（スナップショットの ID か今の表示か）、形式、大きさを info で残す。
- **route policy:** `tests/test_route_policy.py` の `EXPECTED` に、2 つのルートを足す。

## 8. リスク

- **資料の取り扱い:** 資料には、vCenter・ホスト・VM の名前や、イベントとログの内容が入る。外部（ベンダーなど）に渡すときは、利用者が中身を確かめる必要がある。出力したファイルは、管理者が保持期間を短くしても残り続ける。文書に書く。
- **Markdown の解釈:** 外から来た文字列が Markdown として解釈されると、次のことが起きうる。2 章の無害化で防ぎ、GitHub の表示とテストで確かめる。
  - 表が崩れる。
  - 外部の画像を読み込ませる。
  - メンションで通知を飛ばす。
  - 双方向の制御文字で、表示の順を偽装する。

  GFM・CommonMark 以外の表示系は対象外である。
- **CSV の数式:** 表計算のソフトで開いたときに数式として動かないよう、既存の `neutralize_csv_formula` を文字列の列に当てる。
- **集計の負荷と連打:** 今の表示の出力は、表示と同じ集計を 1 回行う。同時実行の上限（503）とレート制限（Issue #301 と同じ枠）が効く。保存した結果の出力も、同じ枠で数える。
- **大きさ:** 結果は最大 8 MiB に抑え、生成はスレッドで行い、同時実行を `aggregation_slot` で抑える。メモリの山は、結果の数倍 × 同時に作る数になる。
- **保存した結果のスキーマ:** スキーマが変わって読めない結果は、409 として扱う（再集計に落ちる画面と同じ考え方）。
- **貼り付け先の上限:** GitHub のコメントなどには長さの上限がある（正確な値は PR C で確かめて文書に書く）。報告書の表を 100 件、1 セル 200 文字に抑えるが、それでも超えるときは、ファイルを添付するよう文書に書く。
