# 画面からリモートログ収集を導入する

ESXi・vCenterのログ収集は「設定 → プラグイン」から追加できます。
vCenterのUUIDを控える作業、TOMLの編集、秘密鍵のファイル配置、`known_hosts`の作成は不要です。
VEAが提供する **VEA Remote Logs**（`vea.remote.logs`）とAsyncSSHは標準の本体に同梱されています。収集は最初は無効です。

## 利用者の手順

### 1. 「設定を始める」を開く

「設定 → プラグイン」で **VEA Remote Logs** の詳細を開き、**設定を始める** を押します。
ボタンがない場合は、管理者へ本体の更新とプラグイン管理機能の有効化を依頼してください。
画面は **収集対象 → SSH接続 → ホスト鍵の確認 → テストと開始** の順に進みます。
各手順の **次へ** で下書きを保存し、**戻る** で入力内容を保ったまま見直せます。

### 2. まず1台だけ収集対象を追加する

**収集対象を追加** を押し、登録済みのvCenterを名前で選びます。
製品はESXiなら `esxi`、vCenter自身なら `vcenter` を選びます。
**ESXi一覧を取得・再試行** で候補を読み込み、対象を選びます。
vCenter自身は候補に「vCenter自身」と表示されます。

一覧の取得に失敗した場合は、ホスト名を手入力して進められます。
接続先IDは自動で付くため入力不要です。一度追加した項目を編集してもIDは維持されます。
選択したら **次へ** を押します。

### 3. SSH接続を登録する

SSH接続先の **接続先を追加・変更** を開き、ホスト名、ポート、SSHユーザー名を入力します。
ホスト名には手順2の候補が入力されます。SSHポートの既定は22です。
SSHユーザー名は管理者から教えてもらってください。vCenter APIの認証情報とは別のものです。

鍵は次のいずれかを選びます。

- 既に登録済みの鍵がある：**登録済みの鍵** から選択します。
- 鍵がない：**鍵の用意方法 → 新しい鍵を生成する** を選び、**アプリで鍵を生成** を押します。
- 管理者から秘密鍵を受け取っている：**秘密鍵をアップロードする** を選び、ファイルを選択して登録します。

**管理者へ渡す公開鍵と登録依頼** を開き、公開鍵をコピー、またはダウンロードして管理者へ渡します。
画面の登録依頼文も一緒に渡し、SSHの有効化、公開鍵登録、ログの読取権限を依頼します。
秘密鍵を管理者へ送る必要はありません。接続時にパスフレーズ入力が必要な鍵は初期版では使えません。
**接続先を保存** を押すと、登録済みのSSH接続先として選択されます。
接続先が選択できたら **次へ** を押します。

### 4. 接続先のホスト鍵を承認する

管理者の準備が済んだら、**ホスト鍵を取得** を押します。
表示されたSHA-256指紋を、管理者から別経路で受け取った指紋と照合します。
一致した場合だけ確認チェックを入れ、**このホスト鍵を承認** を押します。

指紋が違う、または指紋が分からない場合は管理者へ確認してください。
ホスト鍵を取得する操作では、SSH認証やログ読取は行いません。
以後は承認した鍵との一致を毎回検証し、鍵が変わった場合は自動で承認し直しません。
承認できたら **次へ** を押します。

### 5. 接続テストと試し読みを行う

**接続テスト** を押します。下書き保存、SSH認証、ログ読取、必要なコマンドの確認が行われます。
全対象で成功したことを確認します。必要に応じて **試し読み・追加の確認（任意）** を開き、ログの例と実行時間を確認します。
試し読みでは本番のログ保存や読取位置の更新は行いません。

失敗時は画面の案内に従い、SSHユーザー、公開鍵登録、ホスト鍵、読取権限、必要コマンドを確認します。
設定を変更した場合は、接続テストをやり直してください。

### 6. 保存して収集を開始する

テストに成功すると、主ボタンが **収集を開始** に変わります。押すと成功した設定だけが反映され、アプリの再起動なしで定期収集が始まります。
60〜120秒程度待ち、プラグインのvCenter別実行状況とログ登録件数を確認します。
**ログ画面を開く** で対象vCenter・接続先・期間を絞り込んでください。

途中で終える場合は **その他の操作 → 下書きを保存して中断** を押します。現在の収集設定には反映されません。
適用に失敗したときも、元の設定での収集を維持します。
収集中のSSH接続先を変更したい場合は、新しい接続先として登録してテスト後に適用します。

### 7. 問題がなければ対象を増やす

まず1台で、取得量、実行時間、欠落の警告を確認してください。
問題がなければ **収集対象を追加** で対象を増やし、接続テスト後に再度適用します。
同じSSH鍵を複数接続先に使えます。初期版の対象規模はESXi 10台以下です。

## 管理者の初回準備

利用者が画面で設定を始める前に、次を一度準備します。

1. 本体を更新し、通常のPythonインストールまたはDockerイメージを更新します。
   `uv sync --frozen` で公式プラグインと依存関係も導入されます。DB変更は本体起動時に自動適用されます。
2. プラグイン管理（設定の開始・SSH 鍵の生成など）は admin ロールのユーザーだけが行えます。
   admin ロールは信頼できる利用者だけに付与してください（[ログインとロール](user-guides/authentication.md)）。
3. 本体の起動環境に `VEA_PLUGIN_MANAGEMENT_ENABLED=true` と、十分な長さの `VEA_SECRET_KEY` を設定します。
   暗号化キーは既存のものがあればそのまま使い、DBのバックアップと合わせて安全に保管してください。
   未設定の環境ではSSH鍵の生成・登録を拒否します。
4. 対象ESXi・vCenterでSSHを有効化し、利用者が渡した公開鍵を指定アカウントへ登録します。
5. そのアカウントに対象ログの読取権限を与え、SSHホスト鍵のSHA-256指紋を信頼できる経路で利用者へ伝えます。

vCenterでは、そのSSHユーザーがBashコマンドを実行できることも確認します。
プラグインはappliance shellとBashのどちらも判別して、一時的なBashコマンドとして読み取ります。
既定シェルの変更は不要です。Bashアクセスが無効な場合は、管理者が運用方針に従って有効化してください。
シェルの種類とBashアクセスの確認方法は[Broadcomの公式手順](https://knowledge.broadcom.com/external/article?articleNumber=319670)を参照してください。

SSH鍵はDBへ暗号化して保存し、実行時だけ権限を限定した一時ファイルに展開します。
利用者が秘密鍵やknown_hostsをコンテナへマウントする必要はありません。
生成する鍵はRSA 3072ビットです。実際に使用するESXi・vCenter 8系のビルドで、
鍵認証、必要コマンド、appliance shell、ログ形式、ローテーションを検証してから展開してください。

## 既存のTOML設定から移行する

既存のTOMLと外部鍵ファイルによる収集は引き続き利用できます。
画面へ移行する場合だけ **現在の設定を下書きへ読み込む** を押します。
vCenterとの紐付けや接続先IDを維持して読み込みますが、SSH秘密鍵は自動で取り込みません。
SSH接続を画面で登録し直し、承認・接続テスト後に適用してください。元のTOMLは書き換えません。

優先順位は **環境変数 → 適用済みDB設定 → TOML → 既定値** です。
環境変数で固定された設定は画面から変更できません。管理者へ設定の確認を依頼してください。
手動設定の形式は [プラグインREADME](../packages/remote-log-collector/README.md#configuration) を参照できます。

## 収集と検索の既定値

- 60秒間隔、45秒タイムアウト、7日保存。
- 1回・1vCenterあたり最大4MiB、同時SSH接続は最大2件。
- 初回は各現行ファイルの末尾1MiBから取得し、過去のローテーションファイルは取り込みません。
- 初回の過去ログと、変更のない収集済みのローテーションログはファイル情報だけを確認し、圧縮ログの再展開を省きます。
- 最後の時刻付きレコードは継続行をまとめるため次のレコード到着まで待ちます。
- 時刻を解析できない本文も保持し、検索・保存期限には取得時刻を使います。

「ログ」タブで期間、vCenter、接続先、ログ種別、重大度、本文を絞り込み、詳細で全文を表示できます。
イベントの **前後5分のログ** と、ログ詳細からのイベントへのリンクで同じ時間帯を調査できます。

SSH切断・読取失敗時は、そのvCenterの保存と読取位置更新を行いません。他のvCenterは収集を続けます。
現行ログのシンボリックリンクはリンク先の実体を検査し、同じ実体を指す番号付きファイルは重複して読み取りません。
読取中にローテーション・切詰めを検出した場合は、取得量・実行時間の上限内で最大2回再試行します。
再試行にも失敗した場合は保存と読取位置更新を行わず、次の定期実行でやり直します。
ローテーション等で読取位置を復元できない場合は `[collector]` から始まるwarningを保存します。
既にサーバーから消えたログは復元できないため、警告が続くときは管理者へ連絡してください。
